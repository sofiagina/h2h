# Платёжный флоу: заглушка → ЮKassa

## Зачем этот документ

На демо-фронте оплата мгновенная: нажал «Оплатить» — сразу «Оплата прошла»,
через пару секунд «Билет оформлен». Это **заглушка**. Перед реальным запуском
ровно в эту точку встаёт ЮKassa. Задача бэкенда — сделать так, чтобы подмена
заглушки на ЮKassa была заменой одного класса, без переделки заказов.

Пример заказа на демо: заказ `ord_…`, статус «Билет готов», «Оплачено 5 000 ₽» —
но деньги никуда не ушли. С ЮKassa тот же экран появится только после реального
списания.

## Что видит фронт (неизменно для заглушки и для ЮKassa)

`POST /api/v1/orders/{id}/pay` → `{ order, paymentUrl }`.

- `paymentUrl` не null → фронт делает редирект на эту страницу (у ЮKassa —
  их платёжная форма; у заглушки — наша страница с кнопками «Оплатить» /
  «Отклонить»). После оплаты пользователь возвращается на заказ.
- `paymentUrl` == null → платёж подтверждён синхронно, фронт сразу открывает
  заказ (так ведёт себя только совсем простая заглушка; для ЮKassa всегда есть url).
- Дальше фронт опрашивает `GET /orders/{id}` раз в 2 с, пока статус не финальный.

Фронт **не** знает, какой провайдер за этим стоит. Весь провайдер-специфичный
код живёт в бэкенде за интерфейсом `PaymentProvider`.

## Жизненный цикл заказа и денег

Двухстадийная оплата: деньги сначала замораживаются, списываются только после
того, как организатор перевыпустил билет. Не получилось перевыпустить — отмена,
деньги размораживаются без комиссии за возврат.

```
RESERVED ──pay──► (провайдер: hold)
                      │ webhook "деньги заморожены"
                      ▼
                    PAID ──► перевыпуск билета у организатора
                             ├─ успех ─► capture ─► ISSUED
                             └─ отказ ─► cancel  ─► FAILED
```

| Шаг | Заказ | Деньги |
| --- | --- | --- |
| Создал бронь | `RESERVED` | — |
| Нажал «Оплатить» | `RESERVED` | provider.create(capture=false) → редирект |
| Ввёл карту, банк подтвердил | `PAID` | заморожены (hold) |
| Организатор выпустил билет | `ISSUED` | capture — списаны |
| Организатор не смог | `FAILED` | cancel — разморожены |
| Спор решён в пользу покупателя | `REFUNDED` | возврат |

## Точка подмены: один интерфейс

```java
public interface PaymentProvider {
    CreatedPayment create(UUID orderId, long amountKopecks, String idempotenceKey, String returnUrl);
    void capture(String providerPaymentId);
    void cancel(String providerPaymentId);
    ProviderPayment fetch(String providerPaymentId); // перепроверка статуса
}
```

- `FakePaymentProvider` (профиль `dev`, `PAYMENTS_PROVIDER=fake`): `create`
  возвращает `paymentUrl` на нашу страницу `/dev/fake-pay/{id}` с двумя кнопками.
  Кнопка шлёт в наш же вебхук уведомление **того же вида**, что присылает ЮKassa.
- `YooKassaPaymentProvider` (профиль `prod`, `PAYMENTS_PROVIDER=yookassa`): тот же
  интерфейс поверх REST API ЮKassa. Больше в коде заказов не меняется ничего.

Выбор — по настройке `PAYMENTS_PROVIDER`, см. `.env.example`.

## Вебхук

`POST /api/v1/webhooks/yookassa` — одинаков для заглушки и ЮKassa.

- Без JWT.
- Защита: проверка IP отправителя (список IP — из актуальной документации ЮKassa,
  внести в `deploy/nginx/h2h.conf`) **и** перепроверка статуса платежа запросом
  `provider.fetch(...)`. Телу уведомления не доверяем.
- Идемпотентность: событие пишется в `payment_events` с уникальным ключом
  (тип события + id платежа); повторная доставка не обрабатывается дважды.
- Отвечаем `200` быстро, тяжёлую обработку — после ответа.

## Чего не делать

- Не вызывать ЮKassa из кода заказов напрямую — только через `PaymentProvider`.
- Не доверять сумме и статусу из тела вебхука — перепроверять через `fetch`.
- Не угадывать формат API ЮKassa, коды событий, сроки заморозки и комиссии —
  брать из их документации. Поля в этом документе («деньги заморожены», hold,
  capture) — это наша модель, а не дословные имена из API ЮKassa.
- Чеки по 54-ФЗ: отдельный вопрос, согласуется с бухгалтером (агентская схема).
