# CLAUDE.md — h2h-core (бэкенд Hand2Hand)

Бэкенд сервиса передачи билетов по номиналу. Java + Spring Boot + PostgreSQL.
Репозиторий: `git.tunele.ru/h2h/h2h-core`.

## 1. Что это за сервис

Зритель, который не может пойти на концерт, выставляет билет. Покупатель платит **нам**,
организатор по своему API аннулирует билет продавца и выпускает новый на покупателя,
продавцу мы переводим номинал. Организатору мы не платим — он получил деньги при первой продаже.

Наценки нет: цена всегда равна номиналу. Сервисный сбор в пилоте — 0 ₽, но поле `fee` в модели есть.

Два режима гарантии у каждого билета:

| | `organizer` | `escrow` |
| --- | --- | --- |
| Организатор подключён | да | нет |
| Проверка билета | по API организатора | вручную модератором |
| Что получает покупатель | новый билет, старый аннулирован | билет продавца |
| Выплата продавцу | сразу после перевыпуска | через сутки после начала концерта |

## 2. Главное правило: контракт задаёт фронт

Фронт **уже написан** и работает на моке. Бэкенд делается под него, а не наоборот.

Репозиторий фронта: `git.tunele.ru/h2h/Front-AdminPanel` (зеркало — `github.com/sofiagina/h2h`).

- `src/api/types.ts` — все DTO. Сверять поля и типы один в один.
- `README.md` — таблица эндпоинтов с телами запросов и ответов.
- `src/api/mock.ts` — **спецификация поведения**: проверки, переходы статусов, тексты ошибок.
  Если непонятно, что должен вернуть метод, смотреть сюда.

Контракт продублирован в этом репозитории и должен совпадать с фронтом:
- `openapi.yaml` — OpenAPI 3.1 по каждому эндпоинту (схемы, коды, ошибки). Держать в синхроне с `types.ts`.
- `docs/payment-flow.md` — платёжный флоу и точка подмены заглушки на ЮKassa.

Расхождение с контрактом = баг бэкенда. Менять контракт можно, но только вместе с фронтом
и с правкой `types.ts` и `README.md` в том же MR.

Правила контракта:

- базовый путь `/api/v1`, JSON, UTF-8;
- деньги — целые **копейки** (`long`), никогда `double`;
- даты — ISO 8601 со смещением (`2026-11-10T19:00:00+03:00`);
- авторизация `Authorization: Bearer <access JWT>`, refresh — httpOnly-кука, обновление `POST /auth/refresh`;
- ошибки: HTTP-код + `{"code":"SEAT_TAKEN","message":"…"}`. **`message` фронт показывает пользователю как есть** —
  писать по-русски, для человека, без стектрейсов и названий классов;
- коды, на которые фронт реагирует особо: `SEAT_TAKEN`, `AGGREGATOR_UNAVAILABLE`, `RESERVATION_EXPIRED`,
  `UNAUTHORIZED`, `TOO_LARGE` (413);
- `POST /orders` и `POST /orders/{id}/pay` принимают заголовок `Idempotency-Key`: повтор с тем же ключом
  возвращает первый результат, а не создаёт второй заказ или платёж.

## 3. Архитектура

Один Spring Boot процесс, разбитый на модули-пакеты. Отдельных микросервисов на старте нет:
роль шлюза выполняет nginx. Модули общаются через интерфейсы сервисов, **не** через чужие таблицы.

```
browser → nginx (TLS, статика фронта, /api → app, лимиты)
                → app:8080 → PostgreSQL, MinIO (файлы)
ЮKassa  → nginx → /api/v1/webhooks/yookassa
```

Пакеты внутри `ru.h2h.core`:

| Пакет | За что отвечает |
| --- | --- |
| `auth` | вход по одноразовому коду на email, JWT, refresh, роли `customer` и `admin` |
| `catalog` | концерты, площадки, предложения билетов, избранное, лист ожидания |
| `orders` | бронь 15 минут, статусы заказа, выдача билета |
| `payments` | платёжный провайдер, вебхук, возвраты |
| `organizers` | адаптер к билетной системе организатора, Health Monitor |
| `sell` | заявки продавцов, модерация, выплаты |
| `disputes` | споры, сообщения, файлы |
| `admin` | эндпоинты админки, журнал действий |
| `common` | формат ошибок, идемпотентность, outbox, конфигурация |

Статусы заказа: `CREATED` → `RESERVED` → `PAID` → `ISSUED`; ответвления `EXPIRED`, `FAILED`, `REFUNDED`.

## 4. Стек и каркас

Java 17 (локально установлен Temurin 17; если переходим на 21 — менять в `Dockerfile` и `.gitea/workflows/*`),
Spring Boot 3, Maven, Spring Web, Spring Security, Spring Data JPA, Flyway, PostgreSQL, Testcontainers.

Каркаса ещё нет. Создавать его через [Spring Initializr](https://start.spring.io) — **не писать `pom.xml` руками
и не выдумывать версии зависимостей**: взять актуальные с Initializr. Параметры: Maven, Java 17, Spring Boot
последний стабильный, `groupId` `ru.h2h`, `artifactId` `core`, зависимости — Spring Web, Spring Security,
Spring Data JPA, Validation, Flyway Migration, PostgreSQL Driver, Lombok, Testcontainers, Spring Boot Actuator.
Результат распаковать в корень репозитория, рядом с `Dockerfile`.

## 5. Правила кода и данных

- **Миграции только Flyway**, в `src/main/resources/db/migration`, имена `V<N>__<что_делает>.sql`.
  Применённую миграцию не править — писать новую. Схему руками в базе не менять.
- Таблицы в `snake_case`, первичные ключи `uuid`.
- Тестовые данные (концерты, площадки) — отдельной миграцией под профилем `dev`, не в проде.
- Фоновые задачи (снятие просроченных броней, Health Monitor, выплаты по графику) — `@Scheduled`.
  Задача должна быть идемпотентной: повторный запуск не ломает данные.
- Публикация событий — через таблицу `outbox`, не прямым вызовом из транзакции.
- Валидация входа — `jakarta.validation` на DTO; сообщения — по-русски, см. §2.
- Тесты: unit на стейт-машину заказа и адаптеры, интеграционные на Testcontainers (Postgres).
  Без тестов на стейт-машину заказа MR не принимается.

## 6. Безопасность

- **Номер карты в бэкенд не попадает.** Реквизиты выплаты принимает виджет платёжного сервиса и
  возвращает токен. В базе и в ответах API — только маска (`payout.details`: «карта •••• 4242»).
- Персональные данные (email, телефон, ФИО) **не пишутся в логи**. В логах — id сущностей.
- Вебхук платёжного сервиса: без JWT, но с проверкой IP отправителя; телу уведомления **не доверяем** —
  статус платежа перепрашиваем запросом к провайдеру.
- Файлы споров и билетов — в S3 (MinIO), наружу только по ссылке со сроком жизни. Прямого публичного доступа к бакету нет.
- Секреты (пароли БД, ключи платёжного сервиса, JWT) — только через переменные окружения.
  **Никогда не коммитить** `.env`, ключи и токены. Для примера есть `.env.example`.
- Спор может читать и писать только покупатель этого заказа, продавец проданного билета и админ.
  Продавцу не показываются контакты покупателя.

## 7. Платежи

Интерфейс один, провайдер — настройка. Сначала заглушка, потом ЮKassa, без переделки заказов:

```java
public interface PaymentProvider {
    CreatedPayment create(UUID orderId, long amountKopecks, String idempotenceKey, String returnUrl);
    void capture(String providerPaymentId);
    void cancel(String providerPaymentId);
    ProviderPayment fetch(String providerPaymentId);
}
```

- Схема двухстадийная: деньги сначала **замораживаются** (`capture: false`), списываются только после того,
  как организатор перевыпустил билет. Не перевыпустил — `cancel`, деньги размораживаются без комиссии за возврат.
- `FakePaymentProvider` (профиль `dev`): `create` возвращает `paymentUrl` на страницу бэкенда с кнопками
  «Оплатить» и «Отклонить», которые шлют в наш же вебхук уведомление того же вида, что у ЮKassa.
  Путь платежа в деве и в проде одинаковый.
- `YooKassaPaymentProvider` (профиль `prod`): тот же интерфейс поверх их REST API.
  **Не угадывать формат их API, комиссии и сроки заморозки** — брать из актуальной документации ЮKassa.
- События вебхука складывать в `payment_events` с уникальным ключом (тип события + id платежа):
  повторная доставка не должна обработаться дважды. Отвечать 200 сразу, обрабатывать после.

## 8. Локальный запуск

```bash
cp .env.example .env
docker compose up -d          # PostgreSQL, MinIO, Mailpit
./mvnw spring-boot:run        # приложение на :8080
```

Письма с кодами входа — в Mailpit на http://localhost:8025, файлы — в MinIO на http://localhost:9001.
Фронт подключается так: в его `.env` поставить `VITE_USE_MOCK=false`, его dev-сервер уже проксирует `/api` на `localhost:8080`.

## 9. Git и порядок работы

- Ветка `main` защищена. Работать в ветках `feat/<что>`, `fix/<что>`, сливать через pull request.
- **Коммит и пуш — только по явной просьбе.** Не коммитить мимоходом.
- Один MR — один слой задачи: миграция, эндпоинты, тесты. Красный CI не мерджим.
- В описании MR указывать, какие эндпоинты из контракта закрыты, чтобы фронт мог проверить.

## 10. Порядок разработки

Вертикальными кусками: каждый этап включает очередную страницу фронта на настоящем бэкенде.

| Этап | Что делаем | Что заработает во фронте |
| --- | --- | --- |
| 0 | Каркас: Initializr, `/health`, формат ошибок, CI | — |
| 1 | Вход по коду, JWT, refresh | страница входа |
| 2 | Каталог: концерты, билеты, города, избранное | главная, страница концерта |
| 3 | Заказы, бронь, оплата-заглушка, вебхук | оформление и заказ |
| 4 | Адаптер организатора (заглушка), перевыпуск билета | билет в заказе |
| 5 | Заявки продавцов, реквизиты выплаты, модерация | «Продать билет», «Мои продажи» |
| 6 | Споры: переписка и файлы | страница спора |
| 7 | Админка, Health Monitor, журнал действий | админка |

## 11. Чего не делать

- Не придумывать ответы вместо фронта: контракт в `types.ts`, поведение — в `mock.ts`.
- Не угадывать API ЮKassa, API организаторов, пути и версии — спрашивать или брать из документации.
- Не хранить номера карт и не логировать персональные данные.
- Не ходить из одного модуля в таблицы другого.
- Не чинить проблему правкой данных в проде — писать миграцию.
- При развилке (две схемы, два способа) — спрашивать, а не выбирать молча.
