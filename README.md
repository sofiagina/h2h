# Hand2Hand — веб-клиент

Фронт сервиса официальной передачи билетов по номиналу. Построен по ТЗ бэкенда
(«ТЗ: бэкенд платформы вторичной продажи билетов»): тот же набор сущностей, статусы заказа,
деньги в копейках, даты в ISO 8601, `Idempotency-Key` на денежных операциях.

Стек: React 19 + TypeScript + Vite, роутинг — react-router. Других зависимостей нет, стили — один `src/styles.css`.

## Запуск

```bash
npm install
npm run dev
```

Откроется http://localhost:5173. По умолчанию фронт работает на **моках в браузере** — бэкенд не нужен:

- вход — любой email и код `1234`;
- email со словом `admin` (например, `admin@example.test`) открывает админку;
- данные хранятся в `localStorage`, кнопка «Сбросить демо-данные» в подвале возвращает исходное состояние.

Сборка: `npm run build` → папка `dist/` (статические файлы, отдаются любым nginx).

## Подключение к Java-бэкенду

```bash
cp .env.example .env
# в .env: VITE_USE_MOCK=false
npm run dev
```

В dev-режиме Vite проксирует `/api` на `http://localhost:8080` (порт Spring Boot по умолчанию; меняется переменной
`H2H_BACKEND`). На проде фронт и API живут на одном домене, либо задайте `VITE_API_URL`.

## Что есть

| Страница | Путь | Что делает |
| --- | --- | --- |
| Главная | `/` | Как это работает, поиск и фильтр по городу, карточки концертов |
| Концерт | `/events/:id` | Билеты по номиналу, бронь, лист ожидания; пауза продаж, если касса организатора не отвечает |
| Оформление | `/checkout/:orderId` | Таймер брони 15 минут, данные покупателя, оплата |
| Заказ | `/orders/:orderId` | Статус RESERVED → PAID → ISSUED с опросом, электронный билет с кодом |
| Сдать билет | `/sell` | Поиск концерта; если его нет — «Моего концерта нет в списке» (ручная проверка, файл билета, согласие продавца) |
| Вход | `/login` | Вход по одноразовому коду на почту |
| Личный кабинет | `/account` | Мои билеты, сданные билеты, лист ожидания |
| Админка | `/admin` | Кассы организаторов (статус API, история проверок, режим продаж с причиной); модерация заявок без организатора; все заказы |

## Два режима гарантии

| | Организатор подключён (`organizer`) | Организатора нет (`escrow`) |
| --- | --- | --- |
| Откуда концерт | Каталог кассы организатора | Продавец заявил сам, модератор проверил по ссылке |
| Проверка билета | Касса — по номеру заказа | Модератор — по файлу билета и данным заказа |
| Что получает покупатель | Новый билет, старый аннулирован | Билет продавца |
| Деньги продавцу | Сразу — возврат через кассу | Через сутки после начала концерта (`escrow.releaseAt`) |
| Если на входе не пустили | Невозможно: старый билет аннулирован | Покупатель открывает спор в заказе → спор во вкладке «Споры» админки, выплата заморожена → поддержка возвращает деньги или отклоняет. Статус видят покупатель (заказ, «Мои билеты») и продавец («Сданные билеты») |
| Статус заявки продавца | `pending` → `listed` | `review` → `listed` или `rejected` с причиной |

Риск второго режима честно показан на странице концерта и в заказе: продавец может передать один билет нескольким
людям, и мы узнаем об этом только на входе. Каждая такая заявка — заодно контакт организатора, которого стоит подключить.

## Контракт API, который ждёт фронт

Базовый путь `/api/v1`, JSON, авторизация `Authorization: Bearer <access JWT>`. Refresh-токен — httpOnly-кука,
обновление через `POST /auth/refresh`. Ошибки: HTTP-код + `{ "code": "SEAT_TAKEN", "message": "…" }` —
`message` показывается пользователю как есть, поэтому пишется по-русски и для человека.

| Метод | Путь | Тело / ответ |
| --- | --- | --- |
| POST | `/auth/otp` | `{ email }` → 204 |
| POST | `/auth/otp/verify` | `{ email, code }` → `{ accessToken, user }` |
| POST | `/auth/refresh` | → `{ accessToken }` |
| GET | `/users/me` | → `User` |
| GET | `/events?q=&city=&scope=` | → `EventItem[]`. `scope=catalog` (по умолчанию): только предстоящие; концерты без организатора — только пока есть билеты (у подключённых пустой концерт остаётся ради листа ожидания). `scope=sell`: все предстоящие — для поиска в форме продавца |
| GET | `/events/cities` | → `string[]` |
| GET | `/events/{id}` | → `EventItem` (с `salesEnabled`, `minFaceValue`, `availableCount`, `waitlistCount`) |
| GET | `/events/{id}/offers` | → `Offer[]` (только свободные) |
| POST | `/events/{id}/waitlist` | → `WaitlistEntry` |
| POST | `/orders` + `Idempotency-Key` | `{ offerId }` → `Order` в статусе `RESERVED` с `expiresAt` |
| POST | `/orders/{id}/pay` + `Idempotency-Key` | `{ buyer }` → `{ order, paymentUrl }` — фронт уходит на `paymentUrl` эквайринга |
| GET | `/orders/{id}` | → `Order` (фронт опрашивает раз в 2 с, пока статус не финальный) |
| POST | `/orders/{id}/dispute` | `{ message }` → `Order` с `escrow.dispute.status = open` (только для `escrow`, до `releaseAt`, один спор на заказ) |
| GET | `/users/me/orders` · `/users/me/sell-requests` · `/users/me/waitlist` | списки для личного кабинета |
| POST | `/sell-requests` | `SellRequestInput` (`eventId` **или** `newEvent`) → `SellRequest`. Файл билета в демо передаётся только именем — на бэке нужна отдельная загрузка (multipart или presigned URL в S3) |
| GET | `/admin/aggregators` | → `Aggregator[]` с последними 24 проверками |
| PATCH | `/admin/aggregators/{id}` | `{ mode, reason }` → `Aggregator` (пишется в журнал действий) |
| POST | `/admin/aggregators/{id}/check` | внеочередная проверка → `Aggregator` |
| GET | `/admin/orders` | → `Order[]` |
| GET | `/admin/sell-requests` | → `AdminSellRequest[]` (со ссылкой на концерт, файлом, email продавца) |
| POST | `/admin/sell-requests/{id}/review` | `{ approve, comment }` → публикует концерт и билет или отклоняет с причиной |
| GET | `/admin/disputes` | → `AdminDispute[]` (заказ + email продавца), открытые сверху |
| POST | `/admin/disputes/{orderId}/resolve` | `{ refund, comment }` → `refund=true`: заказ `REFUNDED`, спор `refunded`; иначе спор `rejected`, деньги продавцу по графику. Комментарий видят обе стороны |

Типы — в [`src/api/types.ts`](src/api/types.ts); удобно сверять с DTO на Java. Коды ошибок, на которые фронт
реагирует отдельно: `SEAT_TAKEN` (обновить список мест), `AGGREGATOR_UNAVAILABLE` (показать паузу продаж),
`RESERVATION_EXPIRED`, `UNAUTHORIZED` (401 → на вход).

## Структура

```
src/
  api/        types.ts — контракт; http.ts — клиент к бэкенду; mock.ts — мок с теми же правилами
  auth/       контекст входа
  components/ шапка/подвал, карточка концерта, бейджи статусов, таймер, код билета
  pages/      страницы из таблицы выше
  lib/        форматирование денег и дат, хук загрузки
```
